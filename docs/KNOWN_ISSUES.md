# KNOWN_ISSUES

## 7. 公开注册仍不是正式默认策略

- 当前仓库保留了可开启的公开注册能力，但只定义为 demo/staging 场景下的 feature flag。
- 前端已经按 capability 驱动登录页入口、注册页可见性和 `/register` 路由可达性。
- 这不等于正式环境已经具备可默认开放公开注册的治理条件。

影响：
- 即使 capability 可以开启，当前仍缺少正式开放所需的防刷、审计和身份验证能力。
- 交付、验收和对外说明都必须把“demo/staging 可开启能力”与“正式默认策略”明确区分。

日期：2026-03-19

## 1. 真实第三方失败场景尚未系统验证

- 今天已经确认真实百度 OCR 和真实 LLM 的成功返回
- 但“真实失败”这部分还没有形成完整在线烟雾测试矩阵
- 当前不能声称：错密钥、三方超时、三方限流、三方异常结构、网络抖动等都已逐项在线验过

影响：

- 失败路径虽然已经有代码级收口，但真实线上异常的覆盖面仍不足

## 2. 失败路径里的部分验证是 stub 条件，不是在线第三方验证

- `backend/tests/test_failure_paths.py` 主要验证接口语义和数据落库策略
- 这类验证依赖 `patch / monkeypatch`
- 它能证明本地代码在这些分支下怎么处理，不能证明真实百度 / 真实 LLM 在所有异常下都完全符合预期

影响：

- 文档、提交说明和交接口径都必须明确区分“stub 已验证”和“真实第三方已验证”

## 3. 部署环境差异仍可能引入路径与静态资源问题

- 当前路径解析已经不再依赖 `cwd`
- 但部署时仍可能受 `STATIC_URL_PREFIX`、反向代理前缀、CORS、静态目录映射影响
- 前后端如果环境变量不一致，图片访问和跨域行为仍可能出现场景差异

影响：

- 本地可用不自动等于部署环境可用

## 4. 静态资源策略是“统一返回 URL + 前端展示兜底”

- 后端统一返回 `image_url`
- 前端遇到图片丢失时会显示占位
- 当前不会自动补回丢失图片，也没有文件一致性巡检

影响：

- 用户体验不会直接坏成 broken image
- 但资源缺失本身仍然存在，需要运维或后续补偿机制处理

## 5. 数据库迁移治理已建立，但兼容路径仍需严格受限

- 当前仓库已经以 Alembic 作为正式迁移体系
- `Question` 旧契约的运行时补列仍被保留为受限兼容手段
- 如果在非 production 环境误开 `ALLOW_RUNTIME_SCHEMA_MUTATIONS=true`，仍可能让本地行为偏离正式迁移路径

影响：

- 正式环境与共享正式化环境必须坚持先执行 Alembic，再启动应用
- 本地开发或兼容窗口若使用运行时 schema 兜底，必须明确知道这不是正式部署验证

## 6. 鉴权体系仍是最小实现

- 当前前端已接入真实 JWT
- 但只有 access token，没有 refresh token
- 会话治理和过期续签仍是最小方案

影响：

- 本轮交付足够
- 后续如果并发页面、会话时长、权限细粒度要求增加，仍需要补治理
