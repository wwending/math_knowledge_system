# KNOWN_ISSUES

## 1. 真实第三方失败场景尚未系统验证

- 当前已经确认真实百度 OCR 和真实 LLM 的成功返回。
- 但“真实失败”这部分还没有形成完整在线烟雾测试矩阵。
- 当前不能声称：错密钥、三方超时、三方限流、三方异常结构、网络抖动等都已逐项在线验过。

影响：

- 发布说明必须明确区分“正向成功链路已确认”和“真实失败场景尚未系统验完”。

## 2. `backend.tests.test_failure_paths` 主要是本地失败分支验证

- [backend/tests/test_failure_paths.py](/d:/math_knowledge_system/backend/tests/test_failure_paths.py) 主要验证接口语义与数据落库策略。
- 这类验证依赖 `patch / monkeypatch`。
- 它能证明本地代码在这些分支下怎么处理，不能证明真实第三方在所有异常下都完全符合预期。

影响：

- 该测试有工程价值，但不能替代真实第三方异常验收。

## 3. 后端发布门禁依赖已准备好的 Python 依赖环境

- 后端必跑命令需要先安装 `backend/requirements.txt`。
- 如果直接用未安装依赖的裸 Python 解释器执行，测试会因缺少 `fastapi` 等依赖失败。

影响：

- 发布前必须先确认 Python 环境已准备完成。
- 当前门禁是“可执行的最小门禁”，但还不是零准备成本的 CI 门禁。

## 4. 公开注册仍不是正式默认策略

- 当前仓库保留了可开启的公开注册能力，但只定义为 demo/staging 场景下的 feature flag。
- 前端已经按 capability 驱动登录页入口、注册页可见性和 `/register` 路由可达性。
- 这不等于正式环境已经具备可默认开放公开注册的治理条件。

影响：

- 即使 capability 可以开启，当前仍缺少正式开放所需的防刷、审计和身份验证能力。
- 交付、验收和对外说明都必须把“demo/staging 可开启能力”与“正式默认策略”明确区分。

## 5. 数据库迁移治理已建立，但兼容路径仍需严格受限

- 当前仓库已经以 Alembic 作为正式迁移体系。
- `Question` 旧契约的运行时补列仍被保留为受限兼容手段。
- 如果在非 production 环境误开 `ALLOW_RUNTIME_SCHEMA_MUTATIONS=true`，仍可能让本地行为偏离正式迁移路径。

影响：

- 正式环境与共享正式化环境必须坚持先执行 Alembic，再启动应用。
- 本地开发或兼容窗口若使用运行时 schema 兜底，不能把它当成正式部署验证。

## 6. 当前人工 smoke 仍是发布门禁的一部分

- 当前发布门禁没有引入复杂 CI 平台依赖。
- 管理员登录、refresh/logout、强制改密、禁用后旧会话失效、capability 驱动关闭态仍需要人工 smoke 兜底。

影响：

- 当前流程适合 demo 阶段，但仍依赖发布前人工执行与记录。
