# DECISIONS

## 决策 9：公开注册 capability 以前端单一真相源驱动

结论：
- 登录页、注册页和路由守卫统一通过同一条 capability 状态路径读取 `public_signup_enabled`。
- capability=false 与 capability 获取失败在 UI 上都按安全关闭态处理，但内部状态继续保留区分。

原因：
- 分散判断会让页面渲染、路由放行和错误提示出现不一致。
- capability 未确认前如果先展示可提交注册表单，会误导用户进入不确定流程。
- 当前公开注册只适合 demo/staging 按需开启，不应被表达成正式默认策略。

日期：2026-03-19

## 决策 1：先做兼容修复，不推进新模型体系

结论：

- 今天优先把现有链路修到可交付、可追溯，而不是继续推进新模型体系或大改数据结构

原因：

- 当前最直接的交付风险是兼容性和失败路径，不是功能缺失
- 继续推动新模型体系会扩大变更面，反而降低今晚提交的确定性
- 交接需要的是可复现、可解释的稳定状态

## 决策 2：配置先收敛，彻底去掉对 `cwd` 的依赖

结论：

- 路径和运行目录统一交给 `settings` 解析，不再依赖“必须从某个目录启动”

原因：

- `cwd` 依赖会让本地、脚本、部署环境出现低价值差异
- 启动方式越隐式，后续交接越难复现
- 先把路径解析和目录创建规则收敛，后续排障成本最低

## 决策 3：`Question` 旧契约先做运行时兼容，不在今天补正式迁移体系

结论：

- 启动时补齐 `questions` 表缺失旧列，保证老库先可用

原因：

- 今天目标是交付，不是完成数据库治理重构
- 旧库一旦因为字段不齐直接失败，会阻断后续所有链路验证
- 正式迁移体系需要单独设计、回放和验证，不适合和今天的交付收口混在一起

## 决策 4：前端改为真实 JWT，而不是继续保留假 token

结论：

- 登录页必须直接接真实 `/api/v1/auth/token`

原因：

- 假 token 会让正向链路结论失真
- 路由守卫、`401` 处理、历史接口、题库接口都依赖真实鉴权行为
- 只有先接真实 JWT，今天“浏览器已验收”的说法才成立

## 决策 5：`image_url` 由后端统一返回

结论：

- 图片 URL 由后端统一构造，前端只负责消费和兼容过渡

原因：

- 静态路径规则属于后端资源暴露契约，不应散落在多个前端页面里
- 前端继续兼容 `origin_image`，可以平滑承接旧数据
- 统一返回 `image_url` 后，题库、历史、识别结果页面的图片策略才一致

## 决策 6：OCR 全失败不落库

结论：

- OCR 没拿到可用文本时，不生成题目记录

原因：

- OCR 全失败落库只会制造空记录或误导性成功记录
- 这种数据对用户没有价值，还会污染历史和后续排障
- 对今天交付来说，宁可明确失败，也不要留下脏数据

## 决策 7：OCR 成功但 LLM 失败时采用 `partial_success`

结论：

- 这类场景不回退成“全失败”，而是保留 OCR 原文并返回 `partial_success`

原因：

- OCR 结果已经是可用数据，不能因为整理失败就把整条链路判死
- 这样既能减少用户重复上传，也能保留最小可用成果
- 在不扩展模型边界的前提下，这是当前最稳的最小一致性方案

## 决策 8：今天只确认真实第三方成功链路，不夸大失败链路在线验证

结论：

- 文档明确写“百度 OCR 真能返回、LLM 真能返回”
- 同时明确写“真实第三方失败场景在线烟雾测试尚未系统完成”

原因：

- 真实交付文档必须区分已经确认的事实和未系统覆盖的风险
- 把“成功已验证”和“失败未系统验证”混成一句，会直接误导后续提交和交接
